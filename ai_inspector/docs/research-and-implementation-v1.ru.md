# Исследование и порядок реализации v1

Дата проверки публичных источников и локального кода: 28 октября 2026.

Связанные документы: [overview](project-overview-v1.ru.md), [проект контрактов](agent-tools-contracts-v1.ru.md).

Раздел 1 фиксирует уже выполненное исследование. Раздел 2 содержит эксперименты, для которых нужны реальный аккаунт Meta, iPhone, BIM-примеры или сервис Егора. Эти эксперименты не объявляются проведёнными. Новая реализация приложения в рамках подготовки этих документов не выполнялась.

## 1. Ответы на вопросы из обсуждения

### R1. Можно ли использовать Meta/Llama с предопределёнными tools?

**Подтверждено по официальному SDK:** Python-клиент Meta предоставляет синхронный/асинхронный вызов chat completions и потоковую передачу ответа. [Официальный llama-api-python](https://github.com/meta-llama/llama-api-python).

В схеме запроса есть tools с именем, описанием и parameters в JSON Schema, а также tool_choice для автоматического или заданного выбора. В ответе предусмотрены tool_calls с ID и аргументами. Это позволяет построить обычный цикл «модель предложила → backend проверил/выполнил → backend вернул результат». [Схема запроса](https://github.com/meta-llama/llama-api-python/blob/main/src/llama_api_client/types/chat/completion_create_params.py), [схема ответа](https://github.com/meta-llama/llama-api-python/blob/main/src/llama_api_client/types/completion_message.py).

**Решение для v1:** небольшой ModelClient adapter в существующем Python backend, официальный SDK как первый кандидат, собственный ограниченный цикл tools. Отдельный агентский framework не обязателен. В prompt передаются доступные инструменты и правила, но контроль прав и состояний остаётся в коде.

**Граница исследования:** чтение SDK не проверяет доступ аккаунта, актуальный model ID, квоты, регион, стоимость или качество tool-calling. Портал llama.developer.meta.com при проверке не удалось надёжно прочитать; вывод об исполнении tools основан на официальном исходном коде, а live-доступ остаётся обязательным gate. Конкретная модель не выбрана и численные лимиты не выдуманы.

### R2. Нужен ли агенту терминал или исполнение кода?

**Вывод по требованиям:** нет. Все перечисленные действия — создание сессии, сообщение, инструкция, отмена и запуск Geometry — представимы типизированными функциями. SDK — библиотека backend для общения с моделью; он не требует выдавать модели терминал.

Внутренние реализации BIM/Geometry могут содержать произвольные алгоритмы, написанные разработчиками. Агенту предоставляется их ограниченный интерфейс. Если позже появятся параметризованные шаблоны, они становятся новыми tools или параметрами существующих. Генерация кода и его исполнение — отдельная будущая возможность, для которой пока нет продуктовой необходимости.

### R3. Как агент взаимодействует с долгоживущей сессией?

**Вывод по архитектуре и локальному коду:** session живёт в базе, а не в запросе модели. Существующие SQLite sessions, operation receipts, device events, worker leases и Geometry queue уже дают основу для восстановления. См. [storage](../src/ai_inspector/storage.py), [device events](../src/ai_inspector/device_events.py), [workflow](../src/ai_inspector/workflow.py).

**Решение:** добавлять сохраняемые agent_runs/tool_operations и триггеры по событиям поверх этой основы. После ответа агент завершает ход; новое сообщение/проблема/результат запускает следующий. Для ожидания съёмки не нужен бесконечный LLM-запрос, длительный sleep или polling модели. Жизнь workflow не привязана к сроку HTTP-запроса Meta.

В тестовом запуске достаточно существующей очереди на SQLite и одного backend с постоянным диском. База и файлы должны переживать перезапуск процесса. Доступность при выключенном компьютере и отказ диска — отдельные вопросы развёртывания, которые локальная persistence сама по себе не решает.

### R4. Что происходит при уходе iPhone в фон или закрытии приложения?

**Подтверждено Apple:** background URLSession может передавать HTTP/HTTPS-файлы отдельным системным процессом. Для фоновой загрузки после выхода приложения используются upload tasks из файлов. При системном завершении приложение восстанавливает background session с тем же идентификатором. [Background transfers](https://developer.apple.com/documentation/foundation/downloading-files-in-the-background).

**Отдельный случай:** при принудительном закрытии пользователем из переключателя приложений iOS отменяет фоновые передачи и не перезапускает приложение автоматически. Пользователь должен открыть его снова. [Apple: background(withIdentifier:)](https://developer.apple.com/documentation/foundation/urlsessionconfiguration/background(withidentifier:)).

**Решение:** session ID и локальный журнал операций сохраняются независимо от сетевого соединения. При следующем открытии восстанавливаются назначение, недогруженные файлы и pending completion. Прежний WebSocket не обязан выжить в фоне. Устойчивая session не означает непрерывную работу камеры, ARKit или загрузок.

Если ARKit tracking/мировая система координат не восстановились, новый segment_id остаётся внутри прежней session. Требуется договориться с Geometry о поддержке/выравнивании таких сегментов; сам session ID эту задачу не решает.

### R5. Куда загружать batches и как понять, что всё загружено?

**Подтверждено Supabase:** доступны signed upload URLs. В текущем backend они выдаются на ограниченные пути; приём съёмки проверяется по manifest и hashes. [Supabase Swift signed upload URL](https://supabase.com/docs/reference/swift/storage-from-createsigneduploadurl), [существующий iOS контракт](ios-integration.md).

**Решение:** телефон отправляет байты напрямую в Object Storage. Harness получает ссылки, события и счётчики. Manifest определяет полный набор; Geometry стартует только после его серверной проверки и закрепления. Нажатие «Всё снято», удачный PUT и приём completion — три разные стадии.

**Вариант для крупных файлов:** Supabase документирует TUS resumable uploads, включая signed upload tokens. Это кандидат для больших ZIP и нестабильной сети, но не текущая реализованная функция upload-plans. [Resumable uploads](https://supabase.com/docs/guides/storage/uploads/resumable-uploads).

На первом прогоне можно повторять отдельный небольшой файл целиком по действующему протоколу. Необходимость TUS определяется размером реальных файлов и потерями сети. Рецепт для web-клиента нельзя считать готовым решением для native iOS/background URLSession: совместимость нужно проверить отдельно.

### R6. Как передавать проблемы пользователя с телефона в веб?

**Вывод:** нужен сохраняемый двусторонний канал бизнес-сообщений. Сообщение сначала записывается и показывается как реплика пользователя телефона; затем агент может сформировать ответ. Сбой Llama не должен скрывать исходную проблему.

**Решение:** HTTP POST messages для отправки, общие message IDs и доставка событий в device stream и web stream. В вебе предлагается SSE + резервный GET; телефон сохраняет существующий WSS + GET replay. WHATWG определяет reconnect/Last-Event-ID для SSE, но надёжная история событий хранится нашим backend. [Стандарт SSE](https://html.spec.whatwg.org/multipage/server-sent-events.html).

Текущий device WS поддерживает session events и ping/pong, поэтому передача произвольного текста через него пока не реализована. Об этом явно говорит [код API](../src/ai_inspector/api.py).

### R7. Как проверять BIM и выделять одну комнату?

**Подтверждено по первичным источникам:** IfcOpenShell предоставляет IFC validation API и генерацию геометрии. IFC определяет IfcSpace для пространств и связи с пространственной структурой/границами. [IfcOpenShell validation](https://docs.ifcopenshell.org/autoapi/ifcopenshell/validate/index.html), [geometry processing](https://docs.ifcopenshell.org/ifcopenshell-python/geometry_processing.html), [buildingSMART IfcSpace](https://standards.buildingsmart.org/IFC/RELEASE/IFC4_3/HTML/lexical/IfcSpace.htm).

**Вывод для проекта:** IfcOpenShell подходит как кандидат на IFC adapter. Это не готовая проверка качества любой BIM-модели. Необходимо отдельно проверить поддерживаемые схемы, наличие пространств, корректность геометрии, единицы и способы связи стен/дверей с комнатой.

**Предложение v1:** принимать согласованный набор IFC-файлов и выдавать room package с исходными IDs и версиями. Поиск комнаты без результата/с несколькими результатами возвращает структурированную ошибку/кандидатов. Пространственная декомпозиция и границы комнаты могут потребовать разных запросов. [IfcOpenShell element utilities](https://docs.ifcopenshell.org/autoapi/ifcopenshell/util/element/index.html).

Не обещаем, что «одна комната» получается простым удалением всех остальных IfcSpace. Выборка должна сохранять необходимые геометрические зависимости. RVT и конвертация через сторонний сервис остаются отдельной зависимостью.

### R8. Достаточно ли передать Geometry один session ID?

**На уровне agent tool — да. На межсервисной границе нужна ссылка на точный источник.** Иначе ID не сообщает, где лежат данные, закончены ли uploads и какая версия должна обрабатываться.

Существующий adapter уже передаёт job/operation/session IDs, manifest hash и защищённую source URL; принимается callback и опрашивается тот же job. Это сохраняется. [Текущий capture-to-Geometry контракт](capture-to-geometry.md), [workflow](../src/ai_inspector/workflow.py), [обработка результатов](../src/ai_inspector/geometry_results.py).

**Остаётся подтвердить с Егором:** реальный API, RGB-only/RGB-D, требования к poses/intrinsics/depth, единицы/оси, сегменты после ARKit reset, result artifacts, errors, status/cancel. Адрес и договорённость сервиса не выводятся из названия. Mock Geometry в checkout доказывает только путь обмена, а не реконструкцию.

### R9. Нужна ли новая инфраструктура, чтобы начать?

**Вывод по масштабу v1:** начинать с одного Inspector backend, существующей долговременной очереди и внешних BIM/Geometry adapters. Не требуется сначала внедрять отдельный брокер или переносить всю базу. Предметные интерфейсы tools позволяют выделять процессы позже.

Чат, inspection, capture session и model conversation имеют разные сроки жизни. Поэтому «session SDK модели» не используется как продуктовая session. Ошибки и временная недоступность Meta должны оставлять неизменными задания/данные в backend.

E1 нельзя заменить unit mock, E3 — только симулятором сетевых вызовов, E6 — синтетическим PLY. До этих проверок используем формулировки «контракт/adapter подготовлен», а не «система интегрирована».

Неизвестные, которые нужно получить от владельцев: выбранный BIM-провайдер и пример модели; credentials и доступ Meta; реальный Geometry endpoint/identity и поддерживаемый capture profile; версия iPhone app с восстановлением; политика хранения и роли пользователей. Это зависимости конкретных проверок, а не причина останавливать независимые работы.

## 3. Порядок реализации

Это backlog до работающего тестового запуска, без выдуманных сроков. Роли обозначают зоны ответственности, а не уже назначенных людей.

| Этап | Работа | Зависимости | Условие завершения |
|---|---|---|---|
| 0. Подтвердить внешние границы | E1; согласовать минимальный capture profile и Geometry contract; выбрать IFC-кандидат | Доступы владельцев | Известны доступная модель и реальные возможности внешних сервисов |
| 1. Сохраняемый чат и привязки | Chat/message/attachment API, chat-session links, snapshot/events, авторство | Существующий backend | Web message и вложение переживают refresh/restart; повтор не создаёт дубликат |
| 2. Harness и tools | ModelClient, registry, схемы, agent runs, tool operations, leases, budget/time limits | Этап 1, E1 | Реальный Llama выбирает tool, результат сохраняется и объясняется пользователю; restart безопасен |
| 3. Capture-only через агента | session_create/get поверх существующих методов; связать чат и session; общий geometry_ensure_job | Этап 2 | Текстовый запрос без BIM создаёт ровно одну session и доставляет её телефону |
| 4. Сообщения, прогресс, cancel | HTTP messages/instructions/progress/cancel; web events; расширение device events; late-result fencing | Этап 1; подключение к 2/3 | Проблема с телефона видна в вебе, ответ агента доставлен телефону, явная отмена работает |
| 5. Надёжная мобильная работа | Локальная очередь, recovery, background uploads по необходимости, «Всё снято → догрузка → manifest → complete» | Capture API уже есть; события этапа 4 | E3/E8 проходят на устройстве, session ID сохраняется |
| 6. Реальный Geometry прогон | Подключить сервис Егора к существующему adapter; source/status/callback/artifacts, segment support | Этап 0 и реальный capture | E4/E6 проходят, backend сохраняет результат с реальным происхождением |
| 7. BIM-ветка | BIM adapter/job/status, валидация, выбор комнаты, inspection из checked model reference, tools | Этап 0 и 2 | E2/E5: BIM вызывается по смыслу, room context закреплён, неоднозначность решается в чате |
| 8. Общая приёмка | Сквозной прогон и сбои; сверка контрактов iOS/BIM/Geometry, обновление handoff | Этапы 3–7 | Все сценарии раздела 4 выполнены и результаты записаны |

Порядок не требует ждать BIM для проверки съёмки без модели. Мобильное восстановление и согласование Geometry можно вести независимо от написания Llama adapter. После этапов 3/5/6 уже возможен тест capture-only; полной описанной v1 требуется и BIM-ветка.

### Что менять в существующем backend

- Добавить логические модули agent runtime/model adapter, tool registry, chat/messages, attachments и BIM adapter. Конкретная раскладка файлов определяется при реализации.
- Расширить базу миграциями для сообщений, связей chat/session, agent runs, tool operations, instructions и отмены; не заменять существующие session IDs.
- Вынести общее «обеспечить initial Geometry job» из workflow, чтобы auto-path и agent tool делили одну операцию.
- Переиспользовать current capture API, pinned accepted sources, upload plans, durable worker и обработку Geometry results.
- Добавить WebUI chat/events и встроить transport/recovery в настоящий iPhone app. Swift helper в checkout не заменяет эту интеграцию.

## 4. Сценарии приёмки первой версии

1. **Обычный чат:** вопрос без действия со съёмкой не создаёт session и не вызывает BIM tool, даже если файл приложен.
2. **Без BIM:** запрос на съёмку создаёт capture-only session и назначение на разрешённый iPhone.
3. **BIM по смыслу:** косвенная ссылка на проект вызывает BIM tool; неверный файл или отсутствие модели даёт понятный ответ. При неоднозначной комнате агент уточняет, не выбирает случайную.
4. **Доставка и восстановление:** телефон был offline, получил назначение после подключения, сохранил ID, начал съёмку, закрылся и после открытия продолжил ту же session. Новый ARKit segment не подменяет session ID.
5. **Несколько batches:** загружается более одной порции; до завершения нет Geometry job. После «Всё снято» интерфейс различает догрузку и обработку.
6. **Неполный набор:** потерян/повреждён файл, source отклонён, Geometry не запускается. Исправленный manifest с новым completion ID принимается; сетевой replay старого completion не создаёт новый job.
7. **Проблема в комнате:** сообщение телефона видно в вебе с авторством; агент отвечает по смыслу и может передать инструкцию. При временной недоступности Meta исходная реплика остаётся видимой.
8. **Повторы:** timeout создания session/отправки Geometry, повтор message/event/callback и restart backend не создают двойных действий.
9. **Явная отмена:** прекращает workflow и новые команды; offline не считается отменой; поздний Geometry ready не возвращает cancelled в completed.
10. **Реальная геометрия:** сохранён результат настоящего сервиса с правильными source/job/version. Mock явно помечен и не выдаётся за реальную реконструкцию.
11. **Изоляция:** другое устройство/проект не может читать session или получить upload/download grants. Некорректные аргументы модели отклоняются до изменения состояния.
12. **Честный итог:** веб показывает готовую геометрию или объяснимую ошибку. Пока Compare/alignment не реализованы, система не утверждает, что объект соответствует BIM.

## 5. Как фиксировать результаты прогона

Для каждого сквозного прогона сохранить chat/inspection/session/job IDs, версию контракта и capture profile, модель/provider, real/mock origin, время основных переходов и обнаруженные ошибки. Не сохранять в отчёт credentials или временные signed URLs.

Измерять отдельно: подготовка BIM; доставка назначения; окончание съёмки → завершение uploads; completion → source accepted; accepted → Geometry ready; событие/проблема → отображение в вебе и ответ агента. Численные цели по задержке и стоимости утверждаются после реального набора данных.

Факт готовности подтверждается результатами E1–E9 и сценариями приёмки. Наличие endpoint, типов SDK, mock-сервиса или этой документации само по себе не означает завершённую интеграцию.
